crates/fae-engine/src/engine_rt/plan_runtime.rs:535-546
问题描述

对应文档第 6.2、8.5 节和 K3/S5 验收要求。task_result_callback 仅根据 plan.next 返回 Ok 就对 Model/Tool 任务提交 Succeeded，而 next 返回并不证明流消费完成。自定义 Plan 可以保存 ToolResponse 或把消费交给另一协程后继续调度。独立 Rust 复现保存一个尚未读取任何 item 的 ToolResponse 后返回下一批任务，观察任务已经 Succeeded；取消父 Context 后该任务仍保持 Succeeded，ToolResponse::next 在 100ms 超时内未退出。因为终态不可覆盖，父取消无法再将该流任务置为 Cancelled，流的取消订阅也收不到取消。这与第 12 节宣称的消费过程决定流终态不一致。现有流测试通过 RT::exec 检查，未覆盖 Plan 异步回调保留流的路径。

修复建议

删除对受追踪 ModelResponse/ToolResponse 的回调兜底终态提交，让 TrackedModelStream 和 ToolCompletion 在 EOF、Completed、错误或最后消费句柄丢弃时独占提交任务终态。若需兼容其他响应协议，显式区分是否由消费追踪器管理。补充 Plan 保留或异步消费响应时，在消费结束前仍为 Running、父取消可中断消费的验收用例。问题代码：if matches!(task_meta.ty, TaskType::Tool | TaskType::Model) { let state = match &next { Ok(_) => ContextState::succeeded(()), Err(error) => ContextState::failed(error.to_string()) }; task_ctx.set_state(state); }

对应文档第 6.1/6.2 节和 K1/K3 的阶段、开始记录及执行耗时要求。通用 spawn wrapper 只追加 Dispatched；内置 Plan、Model、Tools runtime 补写 Started，但 Memory、Session、Workflow、Mcp 和 Compression 的异步执行路径未补写。独立 Rust 复现通过 Engine 的 RT::spawn 派发 Memory Query 并等待真实回调，栈阶段为 [Dispatched, Succeeded]。EngineContext::append_stack 将 Dispatched 注册为 starts 的兜底，结束条目因而关联派发记录并从派发时刻计算 elapsed_ms；无法区分排队时间与执行时间，也无法获得这些任务实际开始的轨迹。
